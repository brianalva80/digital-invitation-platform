# AMPLOP V20 — Authentication & Database

Cumulative application from V19. Source implementation only; no live Supabase, email, deployment, Codex/Work, or real customer data. The archived V14 engine, V19 local dashboard, landing and five designs remain intact. `/dashboard` now routes to `/account`; `/dashboard.html` is the original public demo and is NOT an authenticated workspace. No billing or publishing in V20.

## Staging setup (authorized later, not executed here)
1. Extract the ZIP. Use Node >=20.9 and a supported LTS. Review compatible patched versions of Next/React/Supabase before `npm install`; keep the verified lockfile, then use `npm ci`. No lockfile generated in this environment. Run `npm test`, `npm run typecheck`, `npm run build`.
2. Create an isolated Supabase staging project only with owner approval. Review `supabase/migrations/202611260001_amplop_v20.sql`; apply once using Supabase CLI or SQL Editor. Do NOT also apply the archived V15 scratch schema. Run `supabase/tests/v20_isolation.sql` in the disposable database using an administrative psql connection and ON_ERROR_STOP=1. All fixtures roll back; never run in production.
3. Enable email/password Auth and email confirmation. Configure project Site URL and exact allowed callback URLs for the actual staging origin: `/account` and `/account?recovery=1`; configure test email delivery and verify redirects. PKCE confirmation/recovery requires the initiating browser context; verify on staging. No SMTP setup or email sent here.
4. Copy `.env.example` to `.env.local`. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to staging project URL and publishable (or legacy anon) key. Never use a service-role/secret key; NEXT_PUBLIC values are browser-visible. Use an access-controlled staging environment and fictional data. `noindex` is not access control.
5. Run `npm run dev`. Visit `/account`. Without valid configuration the account page shows a demo fallback, not a fabricated login. The original static prototype still runs using `python -m http.server 8000 --bind 127.0.0.1 --directory public`, but that server cannot run Auth or the new account route.

## V20 customer workflow
Register/confirm email, login, logout, reset password. Click Muat / buat workspace; one workspace per Auth user. Visit Studio, edit and explicitly Simpan draft, return to account. Click Simpan draft lokal ke cloud and confirm the account and couple name. Cloud save is revision-checked; stale revision rejected, local draft preserved, reload cloud and reconcile manually. Restore cloud to the editor only after explicit confirmation; close other editor tabs before transfer. The original editor remains unchanged, so no autosync. Logout does not clear draft data automatically; explicit Hapus draft lokal action clears both old and current draft keys. Do not share browsers/accounts; local storage remains device-scoped, not user-scoped. The SDK stores authentication session in browser storage; verify storage/XSS risk, CSP, security and session handling in staging. A production design should use isolated authenticated editor sessions and controlled asset storage before real data.

## Data and access decisions
- One new dependency: `@supabase/supabase-js` for PKCE email auth and user-scoped PostgREST/RPC. No service-role key or privileged server endpoint. Client session UI is not a security boundary; database grants, RLS and authenticated RPCs are the intended boundaries. `getUser()` checks active identity before cloud read/save. Account UI drops in-memory snapshots when user changes.
- V20 migration creates `public.amplop_weddings`, `public.amplop_drafts`; unique owner, owner-only SELECT policies, direct mutation grants revoked. `amplop_create_workspace` and `amplop_save_draft` are fixed-search-path security-definer RPCs with auth.uid checks and atomic compare-and-swap revisions. Anonymous calls denied by grants. No staff roles or guest data table yet. V15 reference uses private schema/server approach; V20 deliberately uses public PostgREST schema with RLS and narrowly scoped RPCs. Reconcile later milestones against these actual names instead of applying V15 wholesale.
- Explicit cloud import/export reuses the exact V14 validator and draft format via `lib/cloud/draft.mjs`; adds allowlists for fields, colors/fonts, media data URLs and size. No arbitrary HTML or external media URLs. App-side validation is not a substitute for server validation: DB checks object shape, known template, timezone/schema version and size; a direct authenticated RPC can still write malformed *own* content that passes these basic checks. Strict server-side schema and file-byte validation are a production gate; invalid retrieved content is rejected rather than silently rendered or overwritten.
- Small V14 photo/audio data URLs are stored inline in private owner-scoped draft JSONB for this milestone, preserving exact restore. Not a Supabase Storage bucket implementation. Existing editor limits: 400,000 characters per compressed WebP, 2,800,000 characters audio data URL (~2 MB original upload), 4,100,000 bytes total serialized client draft; DB cap 4,200,000 bytes JSONB text. These are technical staging constraints, not commercial quotas. Dedicated object storage, signed URLs, malware/media inspection, lifecycle cleanup, and larger files remain release gates. No video upload in V20. Backup, data retention/deletion, and privacy policy are not finalized.
- V14 renderer source remains immutable and is copied by `scripts/sync-cloud.mjs` during prepare:demo. Legacy missing experience fields are normalized; unknown/corrupt data rejected. No silent data deletion or migration on login. Test fixtures are not real customer data.
