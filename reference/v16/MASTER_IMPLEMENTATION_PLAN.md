## Execution rules
- Run one milestone only, use repo-specific commands after M0. Each stage produces `RELEASE_EVIDENCE_TEMPLATE.md`-style record plus changed-file list. Store baseline commit and a recoverable branch/tag; use reversible migrations, test rollback/restore on staging. Do not revert unrelated user work. Use forward fix or reviewed rollback rather than destructive reset.
- M2: implement in small slices (renderer/adapter, editor, templates, audio/fonts). Preserve V14 layout and signature openings. Baseline screenshots at 390x844 and desktop 1440; also inspect 320px and landscape. No new design exploration. Avoid needless replatforming; reference source is vanilla HTML/JS and not production auth. Prototype export is test-only; remove or gate in commercial UI. Free preview cannot prevent all copying of browser-rendered content; enforce hosted publication server-side, not DRM promises.
- M3 may precede backend for visual acceptance, but re-test M7 after production adapters. Do not certify physical device compatibility through emulation alone. Owner may use browser/phone to complete UAT. Report lab vs field performance separately. Final font files acquired legally in actual project, retain license notices.
- M4–M6: use V15 contracts as baseline, resolve decisions and missing invariants before migration. Validate SQL in disposable Supabase-compatible environment. Service role bypasses RLS; explicit authorization tests mandatory. Avoid exposure of private schema; test role grants, CSRF, CSP, rate limits. Upload validation must inspect bytes and decode, not just extension.
- Payment provider integration requires sandbox credentials and configuration by owner. Never accept client success redirect as payment proof; verify status and idempotency. No real customer data, secrets, or charges.
- Do not automatically proceed to M8/M9. Guestbook public messages, optional dress code, gift links, custom intro/outro video, and earlier wishlist items need explicit scope; do not conflate RSVP message with public guestbook. Review decision register.

## Quality gates
M1 reference build is reproducible (legacy output path); optional `tools/run_reference_qa.py` uses disposable copy. Legacy test scripts may print failures without nonzero exit, hence runner checks counts and output. It does not replace app-specific tests. Tests with simulated storage, Chromium-only and in-memory loads do not prove native storage, Safari, deployment, accessibility compliance, memory stability, or network performance. Native storage/physical devices/Lighthouse deferred to staging. Record FAIL/BLOCKED honestly. For integration, port test intent, not obsolete selectors: compact audio options require explicit expansion before user clicks. Do not mark blocked gates green.

## Release and rollback
Before any change: record git status and HEAD, list affected modules, agree scope. Preserve current deploy; use preview URL. Before migration: schema diff, backup/restore plan and forward/backward compatibility. On publish rollback: retain previous immutable snapshot and asset references, revert pointer in authorized transaction. On app regression: stop, identify failing commit; rollback only approved changes/deploy, never delete customer records. Record evidence, open bugs, and owner approvals before live release.
