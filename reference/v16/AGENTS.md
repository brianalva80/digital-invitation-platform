# AMPLOP — project instructions for Codex
## Scope and source precedence
- Start with milestone M0 (read-only repository audit). Do not implement any other milestone until owner authorizes it. The package is a reference, not a replacement repository. Existing repository access is not verified.
- Read MASTER_IMPLEMENTATION_PLAN.md, then reference/v14/HANDOFF_V14.md and architecture/ARCHITECTURE_V15.md. Use V14 as the visual and interaction candidate; V15 as proposed backend/business contract; V16 as execution policy. V3 Design Bible is historical creative direction: its Secret Letter-only scope and old technical assumptions are superseded. V13.1 ZIP is rollback/reference only, never the active source.
- Existing working routes, data, deployment, auth and dependencies must be preserved. Reuse compatible framework; Next.js/Supabase/Vercel/Midtrans are proposals, not mandated rewrites. Pin compatible versions after inspection. Do not repeat competitor research or generate new designs.
- Keep five templates distinct. Preserve signature motion, native scrolling, skip/replay, reduced-motion fallback, data personalization, gallery, compact audio controls and no autoplay before user interaction. Do not introduce GSAP, WebGL, or dependencies just for modernization.
- Use a single canonical wedding model. Map server-owned records to V14 presentation data through a tested adapter, not the reverse. No guest/session/secret/base64 blobs in stored public wedding content. Escape all untrusted values by context; no arbitrary user HTML/CSS/URLs. Never promote prototype local RSVP or export as production functionality.
- No unauthorized purchases, live payments, public release, destructive DB changes, account provisioning, or secret exposure. Use synthetic staging data and sandbox credentials only. Do not print env values. Preserve originals and user changes; no force push/reset/clean. Make small reversible patches, checkpoint before each slice. Stop for conflicting requirements, destructive migration, unknown entitlement rules, or inaccessible repo.
- Only execute the named milestone. Prefer existing tests/tools and targeted file inspection. Run relevant tests, summarize changed files and blockers, and stop at the checkpoint. No fabricated test results. A blocked test is not a pass. Never equate historic test counts with current release evidence. Maintain test logs and a concise change log; stop repeated failed attempts after two materially different approaches and report a reproducible blocker.
- For M1+, do not edit files under reference/ or rollback/; work in the application branch or a scratch copy. Do not blindly run SCHEMA_DRAFT.sql. Security and accessibility fixes permitted; log any change in visual behavior for owner review.
- Final design freeze requires owner approval of actual web fonts, assets and staging behavior. No claim of production readiness before release gates.
