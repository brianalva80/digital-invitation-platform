# AMPLOP V15 — Architecture & integration plan
Status: proposed architecture; not deployed, not approved for production. V14 is the visual reference. Existing application repository is not accessible; audit remains a blocking gate. No Codex execution or live service changes in this phase.

## 1. Decisions and boundaries
Use the existing framework if compatible. Otherwise prefer a single Next.js App Router + TypeScript app, Supabase Auth/Postgres/Storage, and Vercel staging. Use a provider adapter for Midtrans sandbox as proposed first option; do not provision a gateway or set actual prices without owner approval. No new microservices. Server validates every mutation and derives identity from verified session, never a client user ID. Private database schema, server-only privileged credentials, RLS deny-by-default defense in depth; explicit authorization is mandatory because service credentials bypass RLS. No direct browser table access in MVP. Keep public route and editor separate. Do not rewrite V14 visual interactions or add GSAP solely for modernization. Pin dependency versions after repo audit.

## 2. Release slices
A (integration): audit original repo, create branch, reproduce existing build and tests; port V14 editor and all five templates; preserve original routes and animation behavior; run local regression and stage. B (MVP SaaS): authentication, wedding workspace, cloud draft/versioning, asset upload, preview, sandbox checkout, entitlement, publish, personalized guest links, RSVP, admin support. C (event day): CSV import/export, QR check-in, private PIN, lucky wheel, staff roles. D (planning): checklist, budget, vendor list, rundown, collaboration. E (optional): seating, memories, WO multi-client, marketplace, AI. Do not build C–E during slice A or B unless owner changes scope. Data model provides extension points without implementing future features now.

## 3. Roles and ownership
Every wedding is a tenant. Owner creates it; editor can modify draft/guest list but cannot pay/publish or grant roles; check-in staff can only check in assigned wedding (slice C); platform support reads minimal metadata, elevated access audited and not implicit. Guest gets public projection, optionally a token-scoped invitation/RSVP session. Never expose all guests, phone numbers, draft, payment, private notes or owner identifiers to guest. Owner can have several weddings. Initial MVP UI owner only; membership model future-ready. Server authorization matrix: owner: all wedding operations except platform administration; editor: read wedding/draft, save draft, upload, guest management; guest: read allowed publication, own RSVP only; public: published non-private invite only; platform support: audited least privilege. No cross-tenant resource IDs accepted without matching wedding ID.

## 4. Data design
Relational records: weddings, wedding_members, drafts, assets, publication_versions, orders, entitlements, guests, rsvps, webhook_receipts, audit_events. Template registry versioned in source initially. Draft JSON contains canonical content and per-template settings; no base64 blobs or guest names embedded in wedding-wide data. Media referenced by asset UUID; public projection resolves only verified assets owned by wedding. Guest identity resolved per request, never accepted from draft. Published snapshots immutable, pointer on wedding selects active snapshot. Store timestamps as timestamptz and timezone as IANA ID; V14 adapter only supports Asia/Jakarta, same day two events, three story entries, three photo slots. MVP enforce these restrictions with clear UI messages; future schema revision allows multi-day/variable slots, WIB/WITA/WIT etc after template QA. Map V14 `couple`, `city`, `country`, `events`, `story`, `photos`, template settings, audio; inject `guest` per request; map asset IDs to trusted URLs or safe adapter-managed image data; never pass arbitrary strings to CSS or URLs. V14 demo `id` becomes stable wedding ID. Demo calendar wording and local RSVP must be removed from production adapters only, visual parity required. Draft may be incomplete; strict publish validator validates all required fields, real calendar dates/time offsets, end>start, ceremony before reception, assets processed, known template/settings, no missing dependencies. See DATA_CONTRACT.json (publish shape), SQL draft and API contract.

## 5. Draft, preview, publish
Draft starts at revision 1. Save uses compare-and-swap (expectedRevision); server increments only on successful save. Client debounces, shows Saving/Saved/Offline/Conflict, never falsely confirms; prevent out-of-order responses and retry only safe operations. Conflict: preserve unsaved changes, reload/merge deliberately. Preview all five designs for free with same data; authenticated private route noindex/no-store. No raw HTML export to unpaid customers in commercial UI (V14 export is test/admin only), while free preview remains unrestricted by template. Paywall enforced on server publication endpoint, not CSS. Proposed commercial rule: one payment unlocks one wedding, all five templates and edits until configured expiry; exact price, duration, refund rules and packages pending owner decision. Payment creates entitlement, not direct publication. Owner chooses Publish; optionally request auto-publish against a specific validated revision, never publish a different revision silently. Publish transaction locks wedding, checks entitlement, revision and owned ready assets, inserts immutable version, updates active pointer; previous public version remains if failure. Subsequent edits update draft until explicit Apply changes; template/music swaps reuse same slug and guest tokens, do not charge again within entitlement. Unpublish revokes public access; expired/refunded entitlement blocks public access according to approved refund policy; stage conservative default suspend pending review. Slug stable unique, reserved words denied, immutable once published in MVP. Private guest views no shared cache; generic public view can be cached only with explicit invalidation and expiry safeguards. noindex default; prevent secret links leaking through referrers or analytics.

## 6. Payment state machine
Create order with server-priced integer IDR snapshot + unique client idempotency key scoped to wedding. Provider order ID unique; retry using same provider order ID/reconcile uncertain response. Redirect result is UX only. Signed webhook: verify provider signature and retrieve canonical provider status, check expected amount/currency/order/environment, map accepted paid status (including fraud checks), transactionally lock order, dedupe normalized event fingerprint and grant entitlement once. Pending/expired/failure cannot downgrade verified paid state; verified refund/chargeback moves to review/suspended per policy. Never trust browser success or raw callback. Repeated/out-of-order callbacks safe; reconciliation job handles delayed or missed callbacks. Store minimal normalized event data, no card data; redact logs. Sandbox only until business terms and provider approval. See Midtrans docs below.

## 7. Asset and audio policy
Private draft storage; server issues short-lived constrained upload intent after quota and ownership checks, random object key by wedding, no public writes. Verify actual bytes/MIME, decode and re-encode images, strip EXIF, size/dimension/duration quotas, scan or reject suspicious files; no client SVG/HTML, only bundled trusted SVG. Proposed audio input maximum 15 MB, allowed MP3/WAV/OGG/M4A only if decoded, normalize to tested web-friendly output (MP3 recommended), maximum duration proposal 10 minutes subject to owner approval; V14 remains 2 MB demo. Process asynchronously or bounded worker; no expensive media work inside latency-sensitive route. States pending/processing/ready/rejected; do not publish pending. Owner attests rights; allow removal/replacement; use immutable asset versions, retain while referenced by publication, garbage-collect after retention. Public media delivery scoped to published assets; private/PIN assets require session-bound or short-lived URLs. No autoplay until user action; pause old iframe on switch; font WOFF2 license review and staging screenshots required. Preserve compact V14 audio UI. Limits proposed, not implemented.

## 8. Guest and RSVP
Owner adds guest display name, optional contact, party limit. Random >=128-bit opaque guest token; store digest only, reveal raw once on issuance; rotate/revoke when needed. Token exchange -> secure HttpOnly scoped guest session; remove token from URL, no third-party tracking. Personalized link remains valid across published design versions. RSVP upsert by unique wedding+guest; server checks session, publication, deadline and party limit; attendance yes/no, count 0 when no, message <=500; transaction + idempotency and rate limiting. No arbitrary guest ID in public body. Generic share link can display invite but no named RSVP unless owner explicitly enables a separately designed anonymous guest flow. Private PIN in phase C: hashed server-side, rate-limited, short-lived session; PIN is not substitute for guest authorization. QR token separate purpose from invite token, check-in transaction idempotent, staff permission, no PII encoded. Lucky wheel draws from eligible checked-in guests, record result and prevent duplicate winners per prize; no wagering.

## 9. Proposed route map
`/`, `/designs`, `/auth/*`, `/studio`, `/studio/[weddingId]/editor`, `/studio/[weddingId]/guests`, `/studio/[weddingId]/billing`, `/studio/[weddingId]/preview`, `/i/[slug]`, `/admin` (separate permissions). API under `/api/v1`. Use explicit errors 400 malformed, 401 unauthenticated, 403 prohibited, 404 absent or hidden cross-tenant, 409 revision/state conflict, 413 too large, 422 semantic validation, 429 rate limited. No credential in URL, logs or client bundle; CSRF protection for cookie-auth mutations, same-site cookies, CSP, output escaping, safe media allowlist, per-tenant quotas, backups/restore drills, structured logs with trace ID and no PII. Preview sandbox isolates scripts and communicates via scoped message channel with source/origin validation; do not inject raw user HTML. No real customer data in staging.

## 10. Future modules
Wedding planner: tasks, assigned members, status, due dates. Budget: categories and expense commitments/paid entries using integer IDR; totals derived, not manually edited. Vendors: vendor records linked to budget lines, contacts, quotes, milestones; private by default. Rundown: ordered time slots and responsibilities. Check-in: unique guest/event attendance, undo audited; lucky wheel results append-only. WO: organization membership mapped to wedding roles, no cross-client access. All use wedding ID and same authorization boundary; build after MVP gates.
