# AMPLOP V23 — Wedding Day Management
Cumulative V17–V23 source candidate, not production-ready. V22 README archived. No Codex/Work, no service provisioning or payment calls. V14 renderer and all five template sources unchanged.

## Staging setup
1. Read AGENTS.md and all RELEASE_GATES_V20–V23 files. Install patched compatible versions and generate lockfile only in authorized staging. `npm run prepare:demo`, `npm test`, `npm run typecheck`, `npm run build`. V23 adds `qrcode` and its dev type package to render standard PNG QR codes, no extra scanner library. Installation and runtime not verified here.
2. Follow archived V20–V22 README for environment and auth/payment. Apply migrations 202611260001 through 004 in order to isolated Supabase after review. Run four rollback-only SQL suites as postgres with ON_ERROR_STOP=1. No real guest data, live payment or deployment. Use HTTPS for secure PIN cookies and camera.
3. In /account, load workspace, save cloud draft, add guest list, configure privacy before publishing, then complete V21 sandbox payment and publish. Public mode retains /i/[slug]; private mode disables generic slug, individual /g/[token] requires PIN, including direct iframe, QR and RSVP routes. Verify actual cookie behavior in browser before sharing any invitation.
4. Owner: load privacy settings, set 6–8 digit PIN, generate or revoke staff code. Copy staff code privately; it appears once per generation. Staff opens /check-in, enters code and loads list. Staff code remains in memory only and is scoped to one wedding. Never put in URL. One shared code, no individually named roles yet. New code revokes old; owner can revoke anytime. Staff may list, check in and export attendance only, cannot manage RSVP, settings, billing, draft or winner draws.
5. Guest opens personal link, unlocks if necessary, views invitation and RSVP, then sees independent QR PNG /g/[token]/qr and fallback code. Staff scans using supported native BarcodeDetector + camera permission; unsupported browsers use pasted code or manual name search. Scan populates code only; staff confirms headcount. Server checks paid publication, authorization, capacity and unique guest ID in a locked transaction. One check-in per invitation, not one per person. No incremental group arrivals, undo, offline mode, or automatic correction; no check-in based solely on RSVP. Link rotation rotates QR credential too.
6. Owner desk shows invited units, checked-in units, actual attending people and pending units. Export CSV includes name,seats,checked_in,checked_at, no credentials/RSVP messages. Owner-only Lucky Wheel picks one checked-in invitation without prior win, using DB UUID randomness; winner and name snapshot persist. Wheel animation decorative, no misleading pointer; result comes from server. A group is one chance, not per-person. No reset or reroll. History blocks deletion of checked-in guest and lowering capacity below actual attendance; workspace deletion needs an explicit lifecycle procedure.

## Implementation and security boundaries
- Migration 004 adds `amplop_event_settings`, `amplop_pin_attempts`, `amplop_checkins`, `amplop_winners`, independent `check_code` on guest row. All new event tables revoke direct access and enable RLS. Service-only RPCs with fixed search path, owner/staff checks and workspace lock serialize event actions. Old V21/V22 RPCs remain service-only internal functions; external routes use V23 wrappers. Do not expose old RPCs via a public API.
- PIN hash salted scrypt; never returned to browser. Signed cookie bound to personal token and current random PIN key, server expiry 8h, HttpOnly/Secure/SameSite=Strict and scoped path. Changing PIN revokes previous proofs; changing personal link revokes old QR and old link. Atomic limit 5 attempts per guest per 15 min, including successful attempts. Needs global/IP limits and abuse monitoring before production. Shared PIN is not individual identity proof; forwardable links/codes are bearer credentials.
- Staff token 256-bit random, SHA-256 digest stored in settings. No expiry yet, manually rotate/revoke. No individual operator attribution beyond owner/staff. Staff cannot access tokens, messages, billing, or draw; attendance names visible for reception purposes. Refresh manual. Need rate limits, audit and retention policies. Owner must protect the code. Existing data already seen by staff cannot be recalled after revocation.
- Owner event endpoint POST /api/event; staff endpoint POST /api/event/staff; both bounded JSON and no-store. Separate secrets; no service-role key in client. PIN gate shares bounded same-origin form with RSVP; gate SQL rechecks current proof and paid publication. Generic private link returns 404, not a PIN screen. RSVP remains external to V14 iframe. QR ticket and PIN HTML preserve V14 shell palette. UI source only, not runtime-verified Next.js.
- Technical choices: 6–8 digit PIN, one staff credential per workspace, one check-in and one win per invitation, no offline mode; not commercial decisions. QR encoder and camera not installed/tested here. QR cannot prevent someone using a copied valid code before the intended guest; staff verify name/identity in person as needed. No automatic individual ticket per seat.
